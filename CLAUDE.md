# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**ひらかたあったかクラウド (Hirakata Attaka Cloud)** — a small community mutual-aid marketplace board. Residents post things they need help with ("困っています") or things they can offer ("私にできること") across three categories: お手伝い (people/labor — originally split into separate ヒト "people" and コト "tasks" categories, merged because users found that distinction confusing, then renamed from 人手), 寄付 (goods, originally labeled モノ then 物資), and 場所提供 (offering/seeking a venue to host a 子ども食堂 — mechanically identical to the other two categories; city staff are expected to be the primary users doing the actual matching for this one via the coordinator screen's manual connect tool, but auto-suggest and participant self-match still work the same as any other category). The app auto-suggests matches between opposite-mode listings in the same category, and a "coordinator" (admin) screen lets a human manually connect people, view stats, and export CSVs.

This is a renamed/rebranded continuation of an earlier pilot called `monomatch-pilot` (see README.md) — the Firebase project is still named `monomatch-pilot` and the GitHub Pages URL may still reflect that name.

## Stack and running the app

Plain static site, **no build step, no bundler, no package.json, no test suite**:
- `index.html` — minimal shell, loads `style.css` and `app.js` as an ES module
- `app.js` — entire application (state, rendering, Firebase calls) in one file, except the 補助金 tab (below)
- `districts.js` — the 小学校区 master list (`DISTRICTS`) and the admin-only 校区ダッシュボード (see "校区ダッシュボード" below)
- `subsidy.js` — the 補助金 (subsidy guide) tab, an ES module imported by `app.js`
- `style.css` — all styling (including `.sb-*` for the subsidy tab and `.ps-*`/`@media print` for its printable forms)
- `firebase-config.js` — Firebase project config + optional `ACCESS_CODE` gate string (not secret — this is a client-side Firebase web config)
- `firestore.rules` — Firestore security rules (deployed manually via Firebase Console, not via CLI/CI)

Firebase SDK (`firebase-app`, `firebase-auth`, `firebase-firestore` v10.12.2) is imported directly from the `gstatic.com` CDN inside `app.js` — there is nothing to `npm install`.

To develop/preview: just serve the directory statically (e.g. `npx serve .` or open `index.html` via a local server — `file://` won't work well with ES modules/Firebase). To deploy: commit and push to `main`; GitHub Pages rebuilds automatically after a few minutes.

There are no lint/test/build commands to run — verify changes by loading the page in a browser against the live Firebase project.

## Architecture

**Single-file vanilla JS app, no framework.** `app.js` holds one global `state` object and a `render()` function that wipes and rebuilds `#root`'s `innerHTML` from scratch on every state change (no virtual DOM, no diffing). Sub-renderers (`renderTop`, `renderRegister`, `renderConnections`, `renderChatTab`, `renderAdmin`, etc.) each return a DOM element for the active tab; `render()` assembles header + tabs + the active panel. Realtime data (`listings`, `connections`, per-thread chat `messages`) is streamed in via Firestore `onSnapshot` listeners that mutate `state` and call `render()` again.

**Identity model is deliberately split from Firebase Auth.** Every user signs in anonymously via Firebase Auth, but the app's actual identity is a separate `profiles/{profileId}` document keyed by a random ID generated client-side (`uid()`). That ID — the "マイページコード" (My Page Code) — is shown to the user on first signup and stored in `localStorage`. Re-entering the code (`onGateRestore`) lets someone recover the same profile from a different browser/device or after clearing site data, independent of the Firebase Auth session. This is intentionally a shared-secret scheme, not real authentication — anyone who has the code can impersonate that profile. `firestore.rules` only checks `request.auth != null` (any signed-in-anonymously user), not code ownership, so all real access control is client-side convention. This tradeoff is documented in README.md and is considered acceptable only for a small trusted pilot group (optionally gated further by the app-wide `ACCESS_CODE` in `firebase-config.js`).

**Firestore data model:**
- `profiles/{profileId}` — `{ id, name, lat, lng, createdAt }`
- `listings/{listingId}` — a need or offer: `{ id, userId, userName, mode: 'need'|'offer', kind: 'お手伝い'|'寄付'|'場所提供', subcat, title, note, deadline, lat, lng, status: 'open'|..., createdAt }` — `kind` went through two renames on live data: `'ヒト'|'モノ'|'コト'` → `'人手'|'物資'` (ヒト/コト merge) → `'お手伝い'|'寄付'` (renamed, and `場所提供` added as a new third category); old records were migrated in place each time
- `connections/{connId}` — a proposed/confirmed pairing between a need listing and an offer listing (renamed from `matches` in the previous `monomatch-pilot` version): `{ id, needId, offerId, title, kind, participants, distanceKm, status: 'proposed'|'connected', connectedBy: 'system'|'coordinator'|<profileId>, connectedByName, connectorUserId, connectedAt, matchedAt, createdAt, hasMessages }` — `connectedByName` is the display name of whoever proposed the connection (null for `'system'` auto-suggestions), used in the coordinator screen's audit trail. `connectorUserId` is set only for `connectedBy:'coordinator'` (the coordinator's own `profileId`) so `myConnections()` also counts them as a participant — they get the thread in their own つながり/チャット tabs and can join the conversation, not just the two matched listing owners. `matchedAt` is set only when a participant clicks 「つながり成立にする」 (status flips to `'connected'`); older records predating this field will be missing it. `hasMessages` starts `false` and flips to `true` the first time anyone (either matched party or a coordinator who joined) sends a chat message (set in the chat send handler, not derived); the coordinator screen's つながり一覧 table filters to `hasMessages === true` only, since most connections are `'system'`-proposed just from matching category/subcat and never actually pursued — pre-existing records were backfilled once by checking whether their `messages` subcollection was non-empty. The チャット tab's badge count is also `hasMessages`-filtered (`つながり`'s badge is not — it counts all of `myConnections()`, matching candidates included).
  - `connections/{connId}/messages/{messageId}` — chat subcollection: `{ senderId, senderName, text, ts }`
- `adminUsers/{authUid}` — presence of a doc keyed by the Firebase Auth UID of a Google-signed-in admin: `{ email, profileName, registeredAt }`. See "Admin role" below. (The old passphrase-based `admins` collection is no longer read or written; its docs are inert.)
- `config/adminEmails` — `{ emails: [...] }`, the admin allow-list; created/edited only in the Firebase Console (rules deny all client access; it's only consulted via `get()` inside the `adminUsers` create rule).

**Matching logic:** `autoSuggestConnections()` runs after every new listing is created and proposes a `connection` for every existing opposite-mode listing with the same `kind` + `subcat` (`proposeConnection`, dedup'd by need/offer pair). Distance between the two parties is computed client-side via `haversine()` using each profile's stored `lat`/`lng`. The coordinator screen's manual-connect tool groups open listings by `kind`+`subcat` (only groups with at least one need and one offer are shown, busiest first) so a coordinator picks from a pre-filtered pair of dropdowns per category rather than two unfiltered global ones (`connectedBy: 'coordinator'`, `connectorUserId` set to the coordinator's own `profileId`); it also surfaces aggregate stats and a per-category bar chart, visible to anyone who reaches the コーディネーター screen (no admin gate) — unlike the two detailed tables below.

**Admin role.** Separate from — and stricter than — the regular マイページコード identity model, because it gates something genuinely sensitive (other people's names/registration details and chat threads). Since `profileId` is unverifiable by Firestore rules, admin status is tied to the Firebase Auth UID instead, via **Google sign-in**: the コーディネーター screen's gate button calls `signInWithPopup(GoogleAuthProvider)` and then `setDoc(doc(db,'adminUsers', uid), {email, ...})`; the rule lets that through only if the token's verified email is in the `config/adminEmails` allow-list (a Firestore doc edited by hand in the Console, so no email addresses or secrets live in the public repo — the old shared passphrase was removed from `firestore.rules` for exactly that reason; it remains in git history but no longer works). A Google account's UID is the same on every device, so admins don't re-register per device. `ensureAuth()` (used by boot/gate) only calls `signInAnonymously` when nobody is signed in, so an admin's Google session survives reloads; `adminLogout()` signs out and falls back to anonymous. Admin-only UI (gated by `state.isAdmin`; `renderAdmin()` returns right after the admin-gate login form when `!state.isAdmin`, so none of the below is even built for a non-admin): the 登録データ一覧 and つながり一覧 tables with duplicate-registration badges (`duplicateGroupSizes`/`dupMark` — same registrant+mode+kind+subcat+title) and CSV export (`exportCsv`), a per-connection chat viewer (`listenAdminChat` / `renderAdminChatViewer`), and a report (`generateReport`) showing average/per-row "registered → matched" and "first chat message → matched" durations. Checked again in `firestore.rules` for `adminUsers` and `subsidyPrograms` writes but *not* for `connections/*/messages` — see caveat below. Caveat: `connections/{connId}/messages` reads are *not* restricted to admins/participants at the Firestore rules level (same `request.auth != null` as everything else) — real per-participant enforcement isn't achievable without linking `profileId` to `authUid` at signup, which hasn't been done. The admin gate only stops a casual user from finding this feature in the UI, not a technically determined one from reading Firestore directly. Setup needed in the Firebase Console: enable the Google sign-in provider, add the hosting domain (e.g. `satogy.github.io`, later the custom domain) to Authentication → Authorized domains, and create `config/adminEmails`.

**Read budget (the pilot runs on the free Spark plan — no Blaze, no Cloud Functions).** Firestore's free quota is 50k reads/day, and the app has no persistent cache, so every page open re-reads whatever its listeners cover. Therefore: `listenListings()` still reads all `listings` (hundreds at most; `status` is always `'open'` — nothing ever closes a listing), but `listenConnections()` reads only the user's own connections via two queries (`participants array-contains me` ∪ `connectorUserId == me`) — never the whole collection, because auto-suggested candidates grow roughly quadratically. `autoSuggestConnections` proposes only the nearest `MAX_AUTO_SUGGEST` (10) opposite-side listings (the coordinator's manual-connect tool can still pair anything; it dedups with `findConnection()`, a `needId`-scoped query, instead of scanning local state). The コーディネーター screen's candidate/成立 totals come from `getCountFromServer` (`loadConnStats`, cached 60 s), and admins additionally subscribe (`attachAdminConnections`, only while that tab is open) to connections with `hasMessages==true` ∪ `status=='connected'` for the ledger/report/chat viewer — untouched candidates are never downloaded. Don't reintroduce a whole-collection `connections` listener; a rough budget is (listings + my connections) reads per open, i.e. ~150 opens/day free at 300 listings. If it ever outgrows that, add `persistentLocalCache` or drop expired listings from the query.

**校区ダッシュボード (district dashboard) — `districts.js`.** Supports the city pilot's KPI "all 44 school districts visible" (identify districts with no 子ども食堂 but with need). Every listing now carries `district` (a 校区 name from `DISTRICTS`, or `'不明'`): the register form has a required select (prefilled from `profile.district`, remembered after each registration), quick offers use the profile's district, and admins can correct any listing's district in the 登録データ一覧 (a per-row select that `updateDoc`s the listing). Older listings have no `district` and count as 不明. `districtInfo/main = { shokudo: { 校区名: number|null } }` holds the number of existing 子ども食堂 per district as known to the city; admins type it into the dashboard (blank = not yet checked, 0 = none). Per-district counts (困りごと / できること / 場所提供 / 成立) are recomputed client-side from the already-loaded listings and the admin-loaded connected connections — nothing is stored. Status per district: 設置状況 未入力 / 未設置・ニーズあり / 未設置・登録なし / 設置済・支援不足 (more needs than offers) / 設置済; headline numbers are 設置状況を把握した校区 and 登録がある校区 out of the list size. **Known gap:** `DISTRICTS` has 42 entries (copied from the city's application workbook) but the pilot's target is 44 — the dashboard shows a warning until the list is reconciled with the city's official one; edit only `districts.js` (the register form and the subsidy wizard import it). Both new rules (`districtInfo`, and `adminUsers`-gated writes) must be published manually in the Firebase Console.

**Tabs:** TOP (deadline-sorted feed of open needs) → 登録する/register (create a listing; also lists the current user's own listings) → つながり/connections (this user's proposed/confirmed connections) → チャット/chat (per-connection realtime thread) → 補助金/subsidy (see below) → コーディネーター/admin (global view + manual matching + stats + CSV export; admin-only report + chat viewer for whoever has completed admin registration).

**補助金 (subsidy) tab — `subsidy.js`.** A guide + simulator + application wizard for people wanting to open a 子ども食堂 and apply for 枚方市's 「子どもの居場所づくり推進事業」 grant (complements the 場所提供 category: the venue is found via つながり, the funding via this tab). Three sub-views: 制度を知る (plain-language explanation), いくらもらえる？ (simulator), 申請書をつくる (11-step wizard that fills 様式第1〜6号 and prints them, optionally with a 会則(例)). Points to keep in mind:
- **All numbers/requirements live in the `PROGRAM`/`TIERS`/`COSTS`/`ORG_REQS`/`EVENT_REQS`/`DOCS` constants at the top of `subsidy.js`**, transcribed from the 令和8年度 募集要項 (令和8年6月改正版) and the city's 申込書類作成用 workbook (tiers A≥40食 ¥10,000 / B 20–39 ¥7,000 / C 10–19 ¥5,500 per session; sessions capped at 1/week; 初期経費 ¥100,000 once; 充実経費 ¥0–5,000 per session, optional). **Update them each fiscal year** against the new 要項. Note the city's own example PDF says class C is "20食未満" while the 要項 says 10–19食; the code follows the 要項.
- **Applicant data never goes to Firestore.** Drafts (which include officers' names/addresses/phones) are stored only in this device's `localStorage` (`attaka_subsidy_draft_v1`) and exported/imported as JSON files, because `firestore.rules` lets any signed-in user read every document. Do not add applicant data to Firestore without fixing that first. Submission to the city happens outside the app (mail/post/hand-delivery after printing/PDF-saving).
- Firestore is used only for `subsidyPrograms/hirakata-kodomo-2026` = `{pdfUrl, pageUrl, note, updatedAt}`, editable by admins from the 制度を知る view (URLs are validated to http/https before saving/linking). This collection's rule in `firestore.rules` must be pasted into the Firebase Console and published manually; until then the tab still works, just without the PDF link/note and with admin save failing gracefully.
- `render()` in `app.js` defers a full re-render while focus is inside an input in `.subsidy-root` (`isSubsidyEditing()`), otherwise a Firestore `onSnapshot` update would rebuild the DOM mid-typing. Inside the tab, input events only update computed displays (`refresh()`, `data-out` elements) instead of re-rendering; structural changes call `rerender()`.
- Amounts are an upper-bound estimate; the city decides eligibility and payment, and new applicants must consult the 子ども青少年政策課 beforehand (the tab says so prominently).
